# Laya 로컬 위키 검색 타당성 보고서

**측정일:** 2026-09-30 · **판정:** 로컬 추론은 가능하지만, 이번 설정의 검색 순위와 라우팅은 운영 기본값으로 쓰기 어렵다.

Laya는 Apple M3 Pro에서 CPU와 MPS로 실행됐다. 다만 소규모 평가에서 문서 수를 늘렸을 때 검색이 안정적으로 좋아지지 않았고, 고정 점수 기준과 수동 분류 라우터도 오답을 걸러내지 못했다. 현재 근거는 “온디바이스 실행 가능성”을 지지하지만 “정확하고 저렴한 답변형 위키 서비스”를 입증하지는 않는다. 이 판정은 아래의 문서 재순위화·컬렉션 분류 실험에 한정된다. 현재 문서의 링크 중 다음 이동을 선택하는 반복 탐색은 아직 평가하지 않았다. [실험 방법과 재현 명령](README.md)

## 무엇을 실제로 시험했나

고정한 모델은 `convaiinnovations/laya-multilingual`, revision `e4e9ddf21a7b1903b7acffd8814ad4307bf63a67`, Laya SDK 0.3.22였다. M3 Pro 11코어, 메모리 36GB, macOS 26.6.2, Python 3.12.13에서 실행했다. 순위 평가는 MPS, `max_len=1024`, 본 평가 `head_max_len=192`로 돌렸다. 평가기는 BM25 후보에서 문서당 최대 두 구간을 골라 Laya 점수를 매기고, 상위 세 문서를 최종 컨텍스트로 남겼다. [Laya 모델 카드](https://huggingface.co/convaiinnovations/laya-multilingual) · [결정형 모델 문서](https://unsloth.ai/docs/models/decision-laya) · [고정 SDK 소스](https://github.com/NandhaKishorM/laya/blob/6d942c92081fbc139e736bbd9ac0023223c29b7f/laya/agent.py)

계정 전체 내보내기는 끝나지 않았다. GitHub 소유 저장소 66개의 인벤토리 중 선택한 공개 저장소 2곳에서 Markdown 문서 27개를 모두 수집했다. 별도로 수집 가능한 로컬 문서는 3,627개였지만 이를 전체 계정 자료로 간주하지 않았다. Notion 캡처 606개도 부분 자료다. 파일당 512 KiB 제한을 적용했고 Markdown 본문만 평가했다. 첨부물은 링크로 남겼으며 내려받거나 OCR하지 않았다.

고정 파일에는 민감한 원문을 넣지 않았다. [summary.json](results/summary.json)은 집계 결과이고 [public-cases.json](results/public-cases.json)은 공개 자료를 대상으로 사전 지정한 질문과 해시 ID만 담는다. 원문 캡처, 개인 문서명·질문·URL, HTTP 본문과 캐시는 로컬 `artifacts/laya-wiki/`에 남겨야 한다.

## 검색 결과

Hit@3은 관련 문서가 상위 세 결과 안에 든 질의 수다. 아래 분모는 각 테스트 코호트의 양성 질의 수이며, 관련성은 사전에 지정한 “알고 있는 정답 문서” 기준이다.

| 평가 | BM25 기준 | Laya 설정 | 관찰 |
| --- | ---: | ---: | --- |
| 47문서 파일럿, 양성 11건 | 6/11 | prefix 상위10: 5/11; 청크 상위10: 7/11; 정규화 상위10: 8/11 | 정규화 47문서 전체에서는 5/11 |
| 공개 GitHub·Confluence 사본 대조, 양성 7건 | 로컬 BM25: 3/7 | 로컬 정규화 상위10: 3/7, 전체27: 3/7; Confluence 상위10: 3/7, 전체27: 2/7 | 상위10 후보에 정답이 포함된 비율은 5/7 |
| 로컬 3,627문서 사용 가능 집합, 양성 4건 | 상위10 기준 2/4 | 정규화 상위10: 2/4, 상위50: 1/4 | 양성 질의 중앙 시간 1.44초와 6.69초 |

후보 누락과 재순위화 오류는 다르게 봐야 한다. 공개 평가에서 상위10 후보가 정답을 포함한 질의는 5/7이므로 나머지 2건은 재순위화만으로 복구할 수 없다. 후보를 모두 넣은 로컬 공개 집합에서는 정규화 순위가 BM25와 같은 3/7이었고, 47문서 파일럿 전체에서는 BM25 6/11보다 낮은 5/11이었다. 파일럿 정규화 순위의 MRR도 상위10에서 0.5833, 전체47에서 0.2892였고 후보 포함률은 각각 9/11, 11/11이었다. 반대로 파일럿 상위10 정규화 결과 8/11은 탐색 신호지만, 같은 작은 코호트에서 나온 값이라 일반화 성능으로 볼 수 없다.

평가 질의는 파일럿 14건(보정 2, 테스트 양성 11, 답이 없는 질의 1)이었다. 라벨은 정답 문서 한 개만 확인했으며 모든 관련 문서를 빠짐없이 표시하지 않았다. 표본도 작고 무작위 표본이 아니므로 백분율을 안정적인 제품 정확도로 해석할 수 없다. 응답 생성, 사용자 효용, 다중 문서 근거 품질은 측정하지 않았다.

고정 임계값 0.7도 신뢰할 수 없었다. 답이 없는 테스트에서 정규화 47문서 결과의 최고 관련도 점수는 0.9977, 세 번째 점수는 0.7068이었다. 따라서 높은 점수나 임계값 조기 종료를 “답을 찾았다”는 확신도로 취급하면 안 된다. 답이 없는 사례가 하나라 이 값은 보정 결과가 아니라 실패 가능성을 보여주는 예다. 인공 tail 입력 한 건에서는 prefix가 9,580 토큰을 잘라냈고 관련도 점수는 prefix 0.2918, 청크 0.6055였다. 같은 한 건에서 기준 문항 순서를 뒤집자 관련도 점수도 0.2918에서 0.1764로 바뀌었다. 이는 견고성 입증이 아니라 단일 프로브의 경고 신호다.

반복 캐시는 동일 질의에서 추가 추론 상태 0개와 같은 순위를 돌려줬다. 이는 정확히 같은 입력의 캐시 재사용 결과일 뿐, 새 질의의 일반 지연시간을 뜻하지 않는다. 캐시 키는 문서 내용·제목, 질의, 구간, 모델 revision, SDK, 장치, 스키마, 길이, 배치 크기와 정책을 반영했다.

## 컬렉션 라우팅과 Confluence 연동

수동으로 만든 5분류 라우터는 문서 본문 토큰 0개, 입력 1,904토큰으로 질문 14개를 평가했다. 실제 라우팅 추론은 네트워크를 차단한 상태에서 실행됐고 모델 처리 시간은 0.775초였다. 보정 세트는 2/2였지만 테스트 분류 정확도는 4/12(33%)였다. 테스트 양성 11건에서 라우팅 후 Hit@3은 1/11, 모든 문서에서 BM25를 실행한 기준은 4/11이었다. 라우터 출력은 현재 후보 검색을 차단하는 필터로 쓰지 말아야 한다. 향후 다시 시험하더라도 참고용 힌트로 제한하는 편이 맞다.

공개 GitHub 자료 27개를 Confluence 사본에 실제로 쓰고 다시 읽어 무결성을 확인했다. [검증한 실험 루트](https://koreaplayer99-confluence-dev.atlassian.net/wiki/pages/viewpage.action?pageId=3506179) 따라서 공개 원본 범위의 왕복 연동은 확인했지만, 개인 자료를 포함한 47문서 이관은 확인하지 못했다. 개인 문서 생성용 `private=true` POST는 HTTP 404를 반환했고 페이지 ID를 받기 전이어서 그 요청 뒤에는 ACL 쓰기가 없었다.

별도로 원문 없이 빈 임시 페이지를 만들어 현재 사용자와 페이지 작성자 읽기를 확인한 뒤, 실제 페이지 제한 PUT을 시도했다. 페이지 생성·사용자 확인·작성자 읽기는 각각 200이었지만 제한 PUT은 403이었다. 새로 GET하고 삭제 전 조건을 확인한 뒤 DELETE 204로 정리했으며, 후속 GET에서 페이지 상태가 `trashed`임을 확인했다. 이 안전한 프로브는 현재 프로필/사이트에서 요청한 제한을 적용하지 못함을 보여준다. 403의 원인이 플랜, 토큰 범위, 계정 권한 또는 공간 권한 중 무엇인지는 확인되지 않았으며 Free 플랜의 증거로 볼 수 없다.

현재 사이트의 과금 플랜은 확인되지 않았고, 검증 루트에 직접 제한이 설정되지 않았으며 상속·익명 접근도 감사하지 않았다. Atlassian 문서에 따르면 Free는 페이지·공간 권한을 사용자 지정할 수 없고 Standard/Premium은 페이지 제한을 지원하지만, 이 실험의 404와 403만으로 현재 플랜을 판정할 수는 없다. [Atlassian 권한 문서](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-in-the-free-edition-of-confluence-cloud/) 개인 Notion 문서는 Confluence에 한 건도 올리지 않았다.

실시간 검색에서 첫 요청은 제한 10개와 같은 10개 후보를 반환해 잘렸을 가능성이 표시됐다. 제한 20개 요청은 후보 17개, HTTP 18회, 응답 253,152바이트를 기록했고 제한에 도달하지 않았다. 두 실행은 각각 2.75초, 2.67초의 단일 측정이므로 속도 차이를 주장할 수 없다. 후보 수가 달라진 결과는 검색 제한 확인일 뿐 관련도 평가가 아니다.

## 자원과 비용

가장 큰 파일럿 실행은 총 434.28초가 걸렸고, 실제 모델 추론은 3,155개 상태에 258.84초였다. 동일 질의의 완전 캐시 재실행은 0.0666초에 새 추론 상태 없이 같은 순위를 냈다. 이는 차가운 첫 실행과 정확히 같은 입력의 캐시 비교다. 프로세스 RSS 최고값은 약 2.74GB, MPS 종료 시 할당량은 약 1.30GB였다. 두 값은 합산하거나 GPU 최고 사용량으로 볼 수 없다. 시험기는 36GB였으므로 Laya 문서에 제시된 4GB 메모리 조건은 검증하지 못했다. [모델 문서](https://unsloth.ai/docs/models/decision-laya)

Laya 로컬 추론은 실제 실행했지만, 답변 생성·채점에 유료 클라우드 LLM을 부른 횟수는 0회였다. API 기준 GPT-6 Luna Standard 단문맥은 100만 입력 토큰당 $0.10, 캐시 입력 $0.01, 출력 $0.50다. 공개 평가에서 Laya 토크나이저로 센 원문 상위10 중앙값 32,258개가 OpenAI 청구 토큰 수와 같다고 가정하면 입력 비용은 약 $0.0032다. 그러나 Laya/mmBERT 토큰은 OpenAI 청구 토큰이 아니므로 실제 비용이나 절감액이 아니다. 산식은 `저장된 OpenAI 입력 토큰 × 단가 / 1,000,000 − 로컬 시간 × 시간당 비용 − 상각된 구축·동기화 비용`이며, 변수와 청구 토큰이 없어 순절감은 계산할 수 없다. Codex 구독/크레딧은 API 가격과 별도로 집계되고 실제 청구액은 확인되지 않았다. [Luna API 가격](https://developers.openai.com/api/docs/models/gpt-6-luna) · [API 가격표](https://developers.openai.com/api/docs/pricing) · [Codex 요금 안내](https://learn.chatgpt.com/docs/pricing)

실험을 준비하고 수집·디버깅하는 데 상당한 Codex 오케스트레이션이 필요했다. 2026-09-30 09:20 KST 목표 스냅샷은 누적 harness 1,186,947 토큰과 5,966초를 기록했다. 이는 청구 입력·출력·캐시 토큰이나 달러가 아니다. 초기 전문 워커는 고정된 GPT-6 Astra 역할을 사용했고, 본 보고서의 초안·정리는 요청대로 GPT-6 Luna max를 사용했다. 부모 모델은 자동 변경되지 않았다. 이 기록만으로 설정비 최소화나 순절감을 주장할 수 없으며, Mac 전력과 사람 시간 비용도 측정하지 않았다. 현재 확인된 것은 로컬 추론 API 호출료가 0이라는 점뿐이다.

## 추가 참고: 링크를 따라가는 결정형 탐색

사용자가 공유한 글은 Jev가 ‘고무오리’에서 ‘컴퓨터 알고리즘’으로 이동하는 사례를 설명한다. TypeSafe의 공식 소개에도 현재 문서의 링크만 따라 목표 문서에 도달하는 Wikiracing 시연이 있으며, ‘Rubber Duck’ 시작 사례를 언급한다. 다만 이번에는 영상을 재생하거나 해당 목표까지의 경로·성공률·비용을 재현하지 않았다. 소개 글은 비교 LLM의 추론 설정이 낮았다는 점과, 선택지가 255개를 넘으면 먼저 점수를 매긴 뒤 선택하는 두 단계 구성을 사용한다는 조건도 밝힌다. 이 시연의 비교 수치를 사내 위키나 로컬 Laya의 성능으로 옮겨 해석할 수는 없다. [TypeSafe 공식 소개](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

이 방식은 문서마다 관련도를 매겨 정렬하는 실험과 다르다. 입력은 질문·현재 문서의 짧은 근거 구간·실제 연결된 문서의 제목과 링크 문맥·방문 이력이고, 출력은 다음에 읽을 후보 하나다. 선택된 문서를 읽은 뒤 새 후보로 같은 판단을 반복한다. Jev의 `Choice`는 미리 제공한 선택지 중 하나를 반환하고, Laya도 상태와 선택지를 받는 인터페이스를 제공하므로 같은 형태의 로컬 선택기를 구성할 수 있다. 이는 인터페이스에 근거한 구현 가능성 판단이며, 탐색 성공을 측정한 결과는 아니다. [Jev Choice](https://docs.typesafe.ai/primitives/choice) · [Laya 모델 카드](https://huggingface.co/convaiinnovations/laya-multilingual)

| 구분 | 기존에 측정한 것 | 별도로 측정해야 할 것 |
| --- | --- | --- |
| 문서 재순위화 | 후보 10~50개의 질문 관련도와 Hit@3 | 다단계 경로의 목표 도달 여부 |
| 컬렉션 분류 | 질문만으로 고정된 문서 집합 선택 | 현재 문서·동적 링크·방문 이력을 사용하는 다음 행동 |
| 목표 | 질문의 알고 있는 정답 문서로 평가 | 이름을 아는 목표 문서 탐색과, 정답 문서를 모르는 질문 탐색을 분리 |

기존 `src/explore.mjs`에는 검색 후보와 현재 본문에서 추출한 링크를 번갈아 읽는 경로가 있다. 다음 실험의 적용 지점은 이 읽기 순서 선택이다. 현재 실험 importer는 원문 링크를 모든 Confluence 사본의 페이지 ID로 바꾸지 않으므로, 사본만으로 연결된 그래프가 만들어졌다고 간주해서도 안 된다. 먼저 원본 ID와 검증한 Confluence 페이지 ID의 대응표로 실제 링크를 해석해야 한다.

비용을 제한한 후속 평가에서는 같은 질문·시작 문서·고정 그래프를 사용해 기존 큐 순서, 링크 제목의 BM25 순서, Laya `Choice` 순서를 비교한다. 우선 후보 5개 이하와 총 8단계의 고정 예산을 적용하고 질문·옵션을 포함한 실제 토큰 사용량과 잘림을 기록한다. 두 번째 경로를 남겨 막다른 길에서 돌아올 수 있게 하고, 방문 중복을 막는다. 연결된 정답 문서를 찾는 데 실패한 경우와, 애초에 경로가 없는 경우를 구분한다. 측정값은 목표 도달률, 읽은 고유 문서 수, 추가 검색 횟수, 단계당 추론·전체 지연시간, 토큰·HTTP 사용량이다. 이 숫자들은 제안한 평가 조건이며 실행 결과가 아니다.

질문 탐색에서는 초기 후보를 저렴한 로컬 검색으로 얻고, Laya가 다음 읽기를 고르도록 하는 조합이 적합한 가설이다. 다만 선택 확률이 높다고 답의 근거가 충분한 것은 아니다. 필요한 주장마다 현재 문서의 실제 근거를 확인한 뒤 LLM에 전달하고, 부족하면 남겨 둔 후보나 새 검색으로 돌아가야 한다. 링크가 풍부하면 읽는 양을 줄일 가능성이 있지만, 연결이 끊겼거나 제목이 모호하면 검색 비용이 오히려 늘 수 있다. Jev 시연만으로 Laya의 판단 품질·보정·비용 절감이 같다고 가정하지 않는다.

## 권고

우선 로컬 BM25 인덱스, 문서 메타데이터, 정규화된 텍스트 구간과 정확한 입력 키 기반 캐시를 사용한다. 현재 측정한 재순위화·컬렉션 분류를 기본 경로로 켜지 않고, 링크 기반 다음 행동 선택은 별도의 가설로 검증한다. 컬렉션 라우팅과 0.7 점수 기준은 검색이나 답변을 차단하는 규칙으로 사용하지 않는다.

실사용 검토를 다시 시작하려면 독립된 더 큰 질문 세트에서 후보 재현율과 순위 품질을 별도로 측정하고, 답이 없는 사례로 점수 보정을 검증해야 한다. 메모리 제한이 중요한 환경은 해당 기기에서 peak RSS와 MPS 최고 메모리를 직접 재측정해야 한다. 이미 승인된 본인 자료 복사는 유효한 제한을 먼저 확인한 뒤 진행한다. 제한을 적용할 수 없는 상태에서 다른 사람도 읽을 수 있는 범위에 게시하려면 그 공개 범위에 대한 별도 승인이 필요하다.
