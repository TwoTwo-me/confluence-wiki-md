# Laya 로컬 위키 검색 타당성 보고서

**갱신일:** 2026-10-01 KST · **판정:** 여러 문서를 연결해 근거를 모으고 통합 답변을 만드는 세 방식의 실제 비교를 완료했다. 직접 읽는 에이전트는 문서를 덜 읽었지만 LLM 토큰을 더 썼다. Laya의 전체 비용 우위는 입증되지 않았다.

최신 실험은 문서 하나의 목적지 도달을 넘어, 최소 3개 문서를 함께 읽어야 하는 복합 질문 4개에 실제 답변과 인용을 생성했다. Laya와 BM25는 각각 총 42문서, GPT-6 Luna max 직접 탐색 에이전트는 27문서를 읽었다. 사전 필수 요점을 포함한 문서는 각각 11개·11개·12개였다. 내용과 출처를 직접 검토한 일반 질문 완성은 Laya 2/4, BM25 2/4, 에이전트 3/4였으며, 인용 ID 오류는 별도로 남겼다. ## 여러 문서를 모아 답한 세 방식 비교

Confluence에서 새로 읽어 검증한 공개 27문서·실제 본문 방향 링크 41개를 사용했다. 초기 파일럿의 기대 문서는 비공개 20개까지 포함해 47개이지만 이번 비교 대상은 검증된 공개 27개뿐이다. 비공개 자료의 추가 게시, 이미지·첨부물 읽기는 0회다. 원문과 Confluence 사본의 별칭으로 링크를 해석하며, 선택 단계는 검증한 스냅샷을 읽는다. 실시간 Confluence 검색 API나 브라우저 이동 속도를 비교한 실험은 아니다. 각 질문은 세 개의 번호 붙은 부분과 이를 연결하는 결론을 요구한다. 총 필수 요점은 29개이며, 원문에서 검증한 근거 문자열로 전체 코퍼스의 최소 집합 덮개를 계산했다. 네 질문 모두 최소 3개 문서가 필요했고 하나 또는 두 문서로 사전 요구 근거를 모두 충족할 수 없었다. 질문은 영어로 직접 골랐고 Q1~Q3은 같은 프로젝트 README에서 시작한다. 독립적인 무작위 표본이나 회사 위키 전체의 일반 성공률은 아니다.

세 방식에 같은 시작 문서, 고유 본문 읽기 최대 12개, 링크 이동·뒤로 가기 최대 24회, 현재 문서의 미방문 목적지 첫 4개를 제공했다. 중복 목적지는 합치고 선택하지 않은 후속 링크도 남긴다. 현재 링크가 소진되면 실제 방문 이력을 따라 `BACK`할 수 있다. `BACK`도 행동으로 계산하지만 이미 보낸 본문을 다시 전송하지 않는다. 세 방식 모두 전체 문서 검색이나 알려진 정답으로 순간이동할 수 없다.

Laya는 읽은 **모든 문서**에서 질문과 관련된 단락을 골라 균형 있게 압축하고 누적 근거로 다음 링크를 선택한다. 상태 700토큰, 링크당 36토큰, SDK 전체 1,024토큰의 한계를 유지한다. 읽은 문서는 모두 상태에 표현되지만 전체 내용이 들어가지는 않는다. BM25는 같은 현재 링크의 이름·경로를 원 질문으로 정렬한다. 두 방식은 예산 또는 연결 구성요소가 소진될 때까지 모은 뒤, 실제 읽은 전체 본문을 새로운 GPT-6 Luna max에 한 번 보내 답한다. 전달된 소스는 ID와 본문이며 평가표는 포함하지 않는다.

직접 탐색 에이전트는 별도의 새 GPT-6 Luna max 실행에서 현재 본문과 링크 메뉴를 읽고 이동하며, 충분하다고 판단하면 먼저 끝낼 수 있다. `./read state`, 현재 선택지의 `./read act`, `./read finish`만 허용했다. 첫 방문의 전체 본문과 이후 캐시 표시를 제공했다. 실제 46개 명령 출력에서 본문·ID·응답 해시와 읽기 순서를 검증했고, 범위 밖 파일·평가표·웹 탐색 및 잘린 본문 출력은 0건이었다. 새로운 실행은 기존 대화·저장소 지침을 가져오지 않는 설정을 사용했다. 작업 디렉터리 밖의 파일을 OS 수준에서 모두 숨긴 보안 격리는 아니며, 협조적인 에이전트의 실제 도구 사용 기록을 감사한 비교다. [Codex 비대화형 실행 문서](https://developers.openai.com/codex/noninteractive)

Laya·BM25는 고정 예산을 쓰고 에이전트는 조기 종료할 수 있으므로, 최종 읽기 수 차이를 다음 링크 선택기만의 인과 효과로 해석하지 않는다. 사후에 동일 읽기 접두어의 근거량과 최초 완성 시점도 계산했다. 정답 ID·근거 문자열은 종료나 선택에 사용하지 않았다.

읽기는 모델에 처음 노출한 고유 본문의 수다. 원시 그래프 전체의 디스크 로딩이나 색인 바이트, HTTP 호출 수와 다르다. “유용 문서”는 사전 필수 요점 하나 이상을 공급한 문서이고, 이미 확보한 요점을 반복하는 문서도 여기에 포함한다. 새 요점을 보탠 문서, 최종 답의 실제 인용으로 요점을 뒷받침한 문서, 전체 답에 필요한 최소 문서 집합은 별도로 계산했다. 불완전한 답의 전체 최소 집합은 `null`이며 이를 0개 문서로 답한 성공으로 계산하지 않는다.

Q1에서 에이전트는 명령 ADR, 분할 뷰 ADR, origin ADR을 함께 읽고 IME 값·저장 소유권·보안 경계를 연결해 맞게 답했다. 원본 인용 4개의 ID에 실제 ID 대신 문서 경로를 썼으므로 자동 인용 계약은 실패했다. 읽은 문서 안에서 네 경로와 인용문의 출처가 모두 고유하게 확인됐다. Laya는 IME의 정확한 값이 빠졌음을 인정했다. BM25 답변은 릴리스 0.3과 로컬 데이터 문서의 관련 내용을 통합했지만 마지막 뷰의 저장 배출 조건을 답하지 못하고 `complete=true`라고 했다. 이 두 대체 문서의 관련 설명을 사전의 정확한 ADR 문자열만으로는 모두 세지 못한다.

Q2에서는 Laya와 에이전트가 versioning 규칙 문서를 찾지 못했지만, 릴리스 0.4 기록에서 `b0ebb0317350`과 전체 SHA를 인용해 12자리 표시와 전체 기록을 설명했다. 실제 해당 릴리스의 값으로는 맞는 답이며 사전의 두 versioning 근거 문자열에는 이 대체 출처가 없었다. 다만 한 릴리스 예시를 일반 UI·릴리스 규칙의 입증으로 평가하지 않았다. 이 한계를 원자료의 직접 검토에 따로 기록했고 라벨을 결과에 맞춰 바꾸지 않았다. BM25는 규칙 문서까지 확보했으며, 불필요한 README 인용 한 개의 ID에는 한 글자 누락이 있었다.

Q3에서 Laya와 에이전트는 명령 ADR·프로젝트 README·설치 ADR의 세 문서로 핵심 답을 완성했다. 에이전트는 읽기 5개 시점에 근거를 모두 확보하고도 10개까지 읽었다. 추가 4번 답변 부분에 잘못 적은 로컬 데이터 ID가 한 개 있었고, 정확한 긴 인용문으로 실제 읽은 출처를 확인했다. BM25는 접두어 시간 제한과 다른 문자 처리 근거를 찾지 못했음을 명시했다. Q4는 세 방식 모두 릴리스·보호 생성·원문 비교의 세 문서를 통합해 맞게 답했다. 소스 `SKILL.md`에 있는 명령은 자료로 분석했으며 실행하지 않았다.

사전 필수 요점 전체를 포함하는 **최소 근거 집합은 성공한 각 질문에서 3문서**다. 예를 들어 Q3은 명령 ADR의 2초·문자 전파, README의 테마 빌드·예약 이름, 설치 ADR의 PNG·CSP를 하나씩 필요로 한다. 단순히 인용을 많이 붙였다는 이유로 필요한 문서 수가 늘어나지는 않는다. 각 답의 최소 집합·중복 근거·무관 문서 목록과 모든 인용 검사는 원자료에 있다.

출력의 추론 토큰은 출력 토큰의 일부이므로 다시 더하지 않는다. 에이전트 입력에는 각 도구 호출까지 누적된 이전 맥락이 반복되며 대부분은 캐시였다. 본문 바이트가 줄어도 전체 LLM 입력은 늘 수 있다. 캐시 제외 입력도 BM25보다 28.2% 많았고 출력·과정 시간도 더 썼다. 이는 이번 실행의 관측값이며 서버 캐시와 실행 순서를 통제한 비용 실험은 아니다. 일부 과정을 병렬로 돌렸으므로 시간 합계를 전체 실험의 벽시계 경과로 해석하지 않는다. 에이전트 열은 도구 실행 시간도 포함하며 이를 따로 분리하지 않았다.

Laya는 SDK 0.3.22, `convaiinnovations/laya-multilingual`의 `e4e9ddf21a7b1903b7acffd8814ad4307bf63a67` revision을 재사용했다. Apple M3 Pro·36GB에서 MPS를 쓰고 네트워크를 차단했다. 새 상태 26개, 입력 16,053토큰, 실제 선택 추론 합계 5.51초, CLI별 peak RSS의 최대는 2,736,963,584바이트였다. 사전 압축으로 누적 문맥을 줄였으며 SDK의 추가 잘림은 0건이다. 동일한 캐시로 네 질문을 다시 실행해 새 추론 0개와 같은 전체 경로를 확인했다. 캐시 실행도 모델을 로딩하므로 전체 시간은 약 31.65초였다. 상주 서비스의 처리량·전력 비용이나 4GB RAM 장치에서의 동작은 측정하지 않았다.

기존 Codex 계정으로 새 직접 탐색 4회, Laya/BM25 결과의 답변 작성 8회, 모델 사용 가능성 확인 1회를 실행했다. 별도 API 키·유료 채점 모델·중복 리뷰 패널은 추가하지 않았다. 답변 과정의 12개 실행 토큰은 위 표에 계측했고, 모델 확인은 입력 13,101·캐시 입력 4,864·출력 6토큰이었다. 부모 Codex의 조율과 구현 작업자 한 명의 토큰은 별도 청구 자료로 캡처하지 못했다. Codex 계정의 크레딧·금액을 API 단가로 환산하지 않았으며 이 호출들이 무료라는 의미도 아니다.

부모가 Python 94개와 Node 81개 회귀 테스트를 실행해 통과했다. 새로운 교차 문서 합산·겹친 근거·최소 집합·첫 완성 접두어·모르는 인용·잘못된 수치·누적 문맥·캐시 경계 테스트 27개를 포함한다. 단일 문서 도착은 3문서 필수 질문에서 1/3만 충족하는 실패 시나리오도 관찰했다. 실제 12개 경로의 175회 링크·BACK, 에이전트의 46개 명령과 27개 최초 본문 노출을 독립적으로 감사했다. 실제 답변 12개와 결론은 부모가 원문과 대조했다. 질문·코드·평가표 해시는 그대로였고 결과를 본 뒤 재추론이나 사례 조율은 하지 않았다. 사용자가 설치를 거절한 LSP는 설치하지 않았으며 구문 검사·테스트·실제 CLI를 사용했다.

이번 결과에서 사용할 수 있는 구조는 누적 근거를 가진 링크 탐색과 출처 검증이다. Laya를 그 선택기에 붙이는 것은 로컬에서 가능하지만 BM25보다 충분한 답을 더 싸게 만든다는 근거는 없다. 비용을 우선하면 BM25를 시작점·후보 선택의 기본으로 두고, 부족한 질문 부분에 한해 제한된 추가 탐색을 수행하는 구성이 맞다. 직접 에이전트는 읽기를 줄이고 Q1의 세 문서 추론을 성공시켰지만 종료 판단과 인용 ID를 검증해야 한다. Laya 자체의 저렴한 26회 선택과 최종 답변까지의 총 비용을 구분해야 한다. 이전 비공개 Confluence 이관의 권한 문제는 이 공개 비교와 별개로 미완료다.

사용자가 요청한 Jev식 목적지 탐색을 별도로 시험했다. 공개 위키의 이름 목표 3개는 Laya와 BM25 모두 도달했고, 로컬 Notion의 이름 목표 3개는 둘 다 하나만 찾았다. Laya는 같은 목표를 찾는 데 문서를 더 읽었다. 질문으로 근거를 찾는 두 사례와 없는 문서를 묻는 대조군에서는 Laya가 근거 없는 도착 판단을 내렸다. 목적지 이름을 아는 탐색과 질문에 충분한 근거가 있는지 판단하는 기능을 구분해야 한다. [추가 측정과 공개 이동 경로](results/destination-walk-summary.json)

Laya는 Apple M3 Pro에서 CPU와 MPS로 실행됐다. 최초 27문서 링크 실험의 일부 개선을 9,434문서로 확장해 확인하니, 양성 질문 10개에서 전역 BM25의 Hit@3은 7개, Laya는 후보 10개에서 2개, 40개에서 1개였다. 공개 2,238문서의 경로 정보를 넣은 별도 선택 실험에서도 Laya와 BM25 모두 6개 중 3개를 찾았다. Notion을 합친 14,002문서의 추가 질문 4개에서도 BM25는 3개, Laya는 후보 10개에서 2개, 20개에서 1개였다. 페이지 속성을 덜어내도 이 결과는 같았다. 이번 자료에서는 BM25를 기본 검색기로 쓰는 편이 정확도와 실행 비용에 맞는다. [실험 방법과 재현 명령](README.md)

## 현재 문서에서 목적지까지 이동한 추가 검증

2026-09-30 22:07:52 UTC에 총 10개 사례와 그래프·평가 라벨 해시를 고정했다. 공개 이름 목표 3개, 질문 2개, 연결되지 않은 목표·존재하지 않는 문서 대조군 각 1개, 로컬 Notion 이름 목표 3개다. 공개 사례는 직접 골랐고 두 질문은 같은 프로젝트 README에서 시작한다. Notion은 서로 다른 시작점과 고유한 기술 문서명을 선택했으며 구조상 최단 경로는 3~4링크다. 목표 이름으로 전체 조상 경로를 알려주지 않았다. 작은 수동 표본의 결과이며 일반 성공률로 볼 수 없다. [고정 공개 사례와 평가 라벨](results/destination-cases.public.json)

탐색기는 현재 문서의 미방문 링크 중 기록 순서의 첫 4개를 선택지로 제공한다. 중복 목적지는 하나로 합치고 창 밖의 링크도 보관한다. 현재 문서의 미방문 링크가 끝나면 방문 이력의 이전 문서로 `BACK`하고, 남아 있던 그 문서의 링크를 고른다. `BACK`도 행동 횟수에 포함되며 본문은 캐시에서 읽는다. 시작점을 포함한 고유 본문 읽기 최대 12개, 이동·뒤로 가기 최대 24회를 적용했다. `laya-greedy`는 막다른 길에서 끝나는 별도 대조 정책이다. 모델이 먼저 뒤로 가기를 계획하는 구현은 아니며, 소진 시 되돌아가는 규칙이다.

이름 목표는 현재 문서의 고유 제목 또는 표시 이름이 사용자가 준 목적지 이름과 일치할 때 끝난다. 질문 목표는 현재 본문으로 답할 수 있는지 Laya가 `ARRIVED`/`CONTINUE`를 고른다. FIFO·BM25에도 같은 Laya 도착 판단기를 써서 다음 링크 선택만 비교했다. 알려진 정답 ID와 요구 근거 문자열은 이동이 끝난 뒤 평가에만 사용했다. 입력은 현재 본문의 질문 관련 단락 최대 280토큰, 현재·방문 문서명, 현재 링크의 이름과 계층 메타데이터다. 상태 최대 700토큰, 선택지당 36토큰, 전체 SDK 입력 1,024토큰을 유지했다. 본문을 미리 잘라 넣는 과정은 있으며, SDK가 상태나 선택지를 추가로 잘랐던 경우는 0개다.

공개 그래프는 원본 27문서·방향 링크 41개와 새로 읽어 검증한 Confluence 사본을 사용했다. 출처 ID 머리글은 모델 본문에서 제거했다. Notion은 기존 캡처의 Markdown 4,415페이지와 부모·자식, DB 행·템플릿, 본문 하이퍼링크를 연결로 표현했다. 출처가 있는 연결 기록 13,178개, 중복 목적지를 합친 방향 연결은 8,800개다. CSV 153문서는 페이지 노드에서 제외했고, 범위 밖·대응 불가 참조 11건을 남겼다. 부모 연결의 순환 검사는 0건이었지만 부모와 자식 사이 왕복 연결이 있으므로 전체 방향 그래프가 비순환이라는 뜻은 아니다. Notion 계층과 DB 메뉴를 모델링한 로컬 그래프이며, 비공개 Notion을 Confluence에 게시한 결과는 아니다.

읽기 합계에는 실패한 사례의 읽기도 포함했다. 공개 로컬·Confluence 사본의 도달 수, 읽기 수, 뒤로 가기 수는 모두 같았고 전체 28개 정책 경로 중 26개가 일치했다. 나머지 둘은 같은 공개 사례의 Laya·greedy 선택 순서가 달랐다. Native의 두 실패는 세 정책 모두 12개 읽기 예산을 소진했다. greedy의 적은 읽기는 조기 막힘이므로 비용 절감 성공으로 평가하지 않는다. Laya는 FIFO보다 공개 목적지 하나를 더 찾았지만 BM25의 도달 수를 개선하지 못했고 본문 읽기도 줄이지 못했다.

실제 성공 경로 하나는 `wiki/architecture.md → wiki/decisions/004-split-panels.md → wiki/releases/0.3.0.md → wiki/decisions/003-origin-isolation.md`다. 현재 문서의 링크를 세 번 선택하고 네 번째 문서의 보이는 제목으로 도착을 확인했다. 다른 공개 사례에서는 Laya가 README에서 디자인·제품·격리·로컬 데이터 문서를 거쳐 네 차례 뒤로 돌아온 뒤 `wiki/README.md → wiki/decisions/002-commands.md`에 도달했다. 그 실제 경로의 고유 7페이지를 Confluence에서 다시 GET했다. 공간 확인을 포함한 HTTP 8회 모두 200이었고 본문·페이지 ID·부모·버전이 검증됐다. 원문 링크와 등록된 Confluence 사본의 대응표를 사용한 읽기 재생이다. 선택 추론은 검증한 스냅샷에서 오프라인으로 했으며 매 단계의 실시간 서버 추론을 시험한 것은 아니다. 원문 링크가 Confluence 내부 링크로 재작성된 것도 아니다.

질문 사례에서는 모든 정책이 요구 근거가 없는 문서에서 멈춰 0/2였다. IME 질문은 필요한 `isComposing`·229 근거가 없는 시작 README에서, origin 질문은 답변 본문 없이 링크 목록을 제공하는 `wiki/README.md`에서 끝났다. 원래 코퍼스 어디에도 없는 실험 문자열 대조군도 시작점에서 `ARRIVED`를 반환했다. 연결되지 않은 이름 목표는 FIFO·BM25·Laya가 도달 없이 해당 구성요소를 소진했고 greedy는 막다른 길에서 끝났다. 탐색 소진 자체를 “전체 위키에 답이 없다”는 판정으로 해석하지 않는다. 이번 질문 결과는 공유 도착 판단기의 실패를 보여주며 세 다음 링크 정책의 관련도 차이를 평가하지 못했다.

전체 새 상태는 55개, 입력 토큰 16,987개, 실제 추론은 5.35초였다. 이는 여러 정책의 상태 캐시를 공유한 비교 실행의 비용이다. Confluence 열은 독립적인 첫 실행 비용이 아니다. 각 표현을 정확히 반복했을 때 새 추론 0개·동일 경로를 확인했지만 CLI가 모델을 다시 로딩하므로 반복 전체 시간은 각각 4.45·4.77·4.48초였다. 토큰 수는 Laya 토크나이저 기준이다. 측정한 Mac은 36GB이며 4GB 기기 조건을 검증하지 않았다. 유료 답변·채점 LLM 호출, 새 비공개 게시, 미디어 읽기는 모두 0회였다. 실제 답변 LLM에 넘긴 청구 토큰이나 전력·운영비를 측정하지 않았고 정확도·읽기 개선도 없어 순비용 절감은 입증되지 않았다.

부모 세션에서 Node 81개와 Python 67개 테스트가 통과했다. 실제 68개 정책 실행 행의 이동·뒤로 가기 434회를 따로 감사했고 Native 이동의 원본 연결 근거 87건도 확인했다. 평가 라벨만 바꿔 실제 CLI를 실행한 28행에서도 이동·종료는 같고 평가 결과만 달랐다. 새 추론은 0개였다. 워커의 실패 후 수정 기록과 부모 검증은 링크 순간이동, 순환·막힘·뒤로 가기, 창 뒤의 링크 보존, 중복 목적지, 제목 충돌, 읽기·행동 예산, 잘못된 SDK 출력, 캐시 경계를 포함한다. TypeScript LSP는 사용자가 설치를 거절한 상태여서 구문 검사와 테스트를 사용했다. 구현 작업자 한 명과 직접 CLI 실행으로 진행했고, 결과를 본 뒤 사례·프롬프트·예산을 조율하거나 유료 채점기를 추가하지 않았다.

이 자료에서 비용을 우선하면 로컬 BM25로 시작 문서를 찾고, 문서 링크·계층과 방문 이력을 유지하는 탐색 구조를 쓰는 쪽이 근거가 있다. Laya는 다음 링크 선택기를 교체할 수 있는 위치에 들어가지만 현재 기본 선택기로 채택할 측정상 이득은 없다. 이름 목표의 도착은 보이는 제목으로 확인할 수 있다. 질문 목표의 자동 종료에는 별도의 근거 검증과 실패 시 추가 탐색이 필요하며, 이번 Laya의 `ARRIVED`를 그대로 신뢰할 수 없다. Free는 페이지 권한 제한을 적용할 수 없고 익명·공개 링크를 지원하지 않는다. 따라서 현재 확인된 사이트에서 외부인이 링크만으로 읽는 상태는 아니다. 앞으로 사람을 초대하면 공간 권한으로 게시한 개인 자료를 읽을 수 있으므로 본인만의 페이지 제한과 같은 보장이 아니다. [Free 권한](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-in-the-free-edition-of-confluence-cloud/) · [공개 링크](https://support.atlassian.com/confluence-cloud/docs/how-secure-are-public-links/)

갱신한 API로도 내용 없는 `private=true` 생성 시험은 404였다. 이 실패 후 개인 원문을 일반 페이지로 바꿔 올리지 않았다. 현재 확인한 공간 권한으로 비공개 GitHub·개인 Notion 텍스트를 복사하는 별도 승인은 대기 중이다. 이미 게시한 공개 자료를 제외한 비공개 11,764문서의 오프라인 이관안은 준비했다. 11,763개는 준비됐고, 비공개 GitHub 한 문서는 Markdown 변환기의 `parentNode` 오류로 제외 사유를 남겼다. 중복 제거·분할·목록 포함 8,816페이지, 준비 텍스트 51,135,665바이트이며 실제 업로드는 0회다. 이관안은 서명 URL 14개와 URL 사용자 정보 18개를 제거한다. 개인 자료의 Confluence 대조 실험과 계정 전체 완전성은 아직 미완료다.

이번 확장에서는 유료 답변·채점 LLM API를 호출하지 않았다. Luna max 사용은 현재 역할을 고정하는 실행 제약과 Aside 계정의 가용 모델 때문에 성사되지 않았다. 동시에 활성화한 구현 작업자는 한 명으로 제한하고, 대량 수집·게시·집계는 직접 스크립트로 처리했다. 이를 Luna로 실행했다고 주장하지 않는다. 목표 드라이버의 중단 시점 스냅샷은 누적 harness 902,663토큰·5,844초였고, 중단 이후의 계속 작업은 포함하지 않는다. 이는 청구 토큰이나 달러가 아니며, 실제 Codex 요금·전력·사람 시간·초기 동기화 비용은 측정하지 않았다. 준비 과정이 저렴했다거나 전체 순비용이 줄었다는 결론도 낼 수 없다.

현재 근거에 맞는 구성은 로컬 동기화와 BM25로 후보를 찾고, 작은 실제 근거 구간을 최종 LLM에 전달하는 방식이다. Laya의 예측값을 근거 충분성으로 사용하지 않는다. 다음 후보를 더 읽는 흐름은 남겨 둘 수 있지만 그 조건은 별도 검증이 필요하다. 이번 추가 캠페인에서는 Laya를 기본 검색·재정렬기로 채택할 근거가 없었다.

## 무엇을 실제로 시험했나

고정한 모델은 `convaiinnovations/laya-multilingual`, revision `e4e9ddf21a7b1903b7acffd8814ad4307bf63a67`, Laya SDK 0.3.22였다. M3 Pro 11코어, 메모리 36GB, macOS 26.6.2, Python 3.12.13에서 실행했다. 순위 평가는 MPS, `max_len=1024`, 본 평가 `head_max_len=192`로 돌렸다. 평가기는 BM25 후보에서 문서당 최대 두 구간을 골라 Laya 점수를 매기고, 상위 세 문서를 최종 컨텍스트로 남겼다. [Laya 모델 카드](https://huggingface.co/convaiinnovations/laya-multilingual) · [결정형 모델 문서](https://unsloth.ai/docs/models/decision-laya) · [고정 SDK 소스](https://github.com/NandhaKishorM/laya/blob/6d942c92081fbc139e736bbd9ac0023223c29b7f/laya/agent.py)

계정 전체 내보내기는 끝나지 않았다. GitHub 소유 저장소 66개의 인벤토리 중 선택한 공개 저장소 2곳에서 Markdown 문서 27개를 모두 수집했다. 별도로 수집 가능한 로컬 문서는 3,627개였지만 이를 전체 계정 자료로 간주하지 않았다. Notion 캡처 606개도 부분 자료다. 파일당 512 KiB 제한을 적용했고 Markdown 본문만 평가했다. 첨부물은 링크로 남겼으며 내려받거나 OCR하지 않았다.

고정 파일에는 민감한 원문을 넣지 않았다. [summary.json](results/summary.json)은 집계 결과이고 [public-cases.json](results/public-cases.json)은 공개 자료를 대상으로 사전 지정한 질문과 해시 ID만 담는다. 원문 캡처, 개인 문서명·질문·URL, HTTP 본문과 캐시는 로컬 `artifacts/laya-wiki/`에 남겨야 한다.

## 검색 결과

Hit@3은 관련 문서가 상위 세 결과 안에 든 질의 수다. 아래 분모는 각 테스트 코호트의 양성 질의 수이며, 관련성은 사전에 지정한 “알고 있는 정답 문서” 기준이다.

| 평가 | BM25 기준 | Laya 설정 | 관찰 |
| --- | ---: | ---: | --- |
| 47문서 파일럿, 양성 11건 | 6/11 | prefix 상위10: 5/11; 청크 상위10: 7/11; 정규화 상위10: 8/11 | 정규화 47문서 전체에서는 5/11 |
| 공개 GitHub·Confluence 사본 대조, 양성 7건 | 로컬 BM25: 3/7 | 로컬 정규화 상위10: 3/7, 전체27: 3/7; Confluence 상위10: 3/7, 전체27: 2/7 | 상위10 후보에 정답이 포함된 비율은 5/7 |
| 로컬 3,627문서 사용 가능 집합, 양성 4건 | 상위10 기준 2/4 | 정규화 상위10: 2/4, 상위50: 1/4 | 양성 질의 중앙 시간 1.44초와 6.69초 |

후보 누락과 재순위화 오류는 다르게 봐야 한다. 공개 평가에서 상위10 후보가 정답을 포함한 질의는 5/7이므로 나머지 2건은 재순위화만으로 복구할 수 없다. 후보를 모두 넣은 로컬 공개 집합에서는 정규화 순위가 BM25와 같은 3/7이었고, 47문서 파일럿 전체에서는 BM25 6/11보다 낮은 5/11이었다. 파일럿 정규화 순위의 MRR도 상위10에서 0.5833, 전체47에서 0.2892였고 후보 포함률은 각각 9/11, 11/11이었다. 반대로 파일럿 상위10 정규화 결과 8/11은 탐색 신호지만, 같은 작은 코호트에서 나온 값이라 일반화 성능으로 볼 수 없다.

평가 질의는 파일럿 14건(보정 2, 테스트 양성 11, 답이 없는 질의 1)이었다. 라벨은 정답 문서 한 개만 확인했으며 모든 관련 문서를 빠짐없이 표시하지 않았다. 표본도 작고 무작위 표본이 아니므로 백분율을 안정적인 제품 정확도로 해석할 수 없다. 응답 생성, 사용자 효용, 다중 문서 근거 품질은 측정하지 않았다.

고정 임계값 0.7도 신뢰할 수 없었다. 답이 없는 테스트에서 정규화 47문서 결과의 최고 관련도 점수는 0.9977, 세 번째 점수는 0.7068이었다. 따라서 높은 점수나 임계값 조기 종료를 “답을 찾았다”는 확신도로 취급하면 안 된다. 답이 없는 사례가 하나라 이 값은 보정 결과가 아니라 실패 가능성을 보여주는 예다. 인공 tail 입력 한 건에서는 prefix가 9,580 토큰을 잘라냈고 관련도 점수는 prefix 0.2918, 청크 0.6055였다. 같은 한 건에서 기준 문항 순서를 뒤집자 관련도 점수도 0.2918에서 0.1764로 바뀌었다. 이는 견고성 입증이 아니라 단일 프로브의 경고 신호다.

반복 캐시는 동일 질의에서 추가 추론 상태 0개와 같은 순위를 돌려줬다. 이는 정확히 같은 입력의 캐시 재사용 결과일 뿐, 새 질의의 일반 지연시간을 뜻하지 않는다. 캐시 키는 문서 내용·제목, 질의, 구간, 모델 revision, SDK, 장치, 스키마, 길이, 배치 크기와 정책을 반영했다.

## 컬렉션 라우팅과 Confluence 연동

수동으로 만든 5분류 라우터는 문서 본문 토큰 0개, 입력 1,904토큰으로 질문 14개를 평가했다. 실제 라우팅 추론은 네트워크를 차단한 상태에서 실행됐고 모델 처리 시간은 0.775초였다. 보정 세트는 2/2였지만 테스트 분류 정확도는 4/12(33%)였다. 테스트 양성 11건에서 라우팅 후 Hit@3은 1/11, 모든 문서에서 BM25를 실행한 기준은 4/11이었다. 라우터 출력은 현재 후보 검색을 차단하는 필터로 쓰지 말아야 한다. 향후 다시 시험하더라도 참고용 힌트로 제한하는 편이 맞다.

공개 GitHub 자료 27개를 Confluence 사본에 실제로 쓰고 다시 읽어 무결성을 확인했다. [검증한 실험 루트](https://koreaplayer99-confluence-dev.atlassian.net/wiki/pages/viewpage.action?pageId=3506179) 따라서 공개 원본 범위의 왕복 연동은 확인했지만, 개인 자료를 포함한 47문서 이관은 확인하지 못했다. 개인 문서 생성용 `private=true` POST는 HTTP 404를 반환했고 페이지 ID를 받기 전이어서 그 요청 뒤에는 ACL 쓰기가 없었다.

별도로 원문 없이 빈 임시 페이지를 만들어 현재 사용자와 페이지 작성자 읽기를 확인한 뒤, 실제 페이지 제한 PUT을 시도했다. 페이지 생성·사용자 확인·작성자 읽기는 각각 200이었지만 제한 PUT은 403이었다. 새로 GET하고 삭제 전 조건을 확인한 뒤 DELETE 204로 정리했으며, 후속 GET에서 페이지 상태가 `trashed`임을 확인했다. 이 안전한 프로브는 현재 프로필/사이트에서 요청한 제한을 적용하지 못함을 보여준다. 403의 원인이 플랜, 토큰 범위, 계정 권한 또는 공간 권한 중 무엇인지는 확인되지 않았으며 Free 플랜의 증거로 볼 수 없다.

현재 사이트의 과금 플랜은 확인되지 않았고, 검증 루트에 직접 제한이 설정되지 않았으며 상속·익명 접근도 감사하지 않았다. Atlassian 문서에 따르면 Free는 페이지·공간 권한을 사용자 지정할 수 없고 Standard/Premium은 페이지 제한을 지원하지만, 이 실험의 404와 403만으로 현재 플랜을 판정할 수는 없다. [Atlassian 권한 문서](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-in-the-free-edition-of-confluence-cloud/) 개인 Notion 문서는 Confluence에 한 건도 올리지 않았다.

실시간 검색에서 첫 요청은 제한 10개와 같은 10개 후보를 반환해 잘렸을 가능성이 표시됐다. 제한 20개 요청은 후보 17개, HTTP 18회, 응답 253,152바이트를 기록했고 제한에 도달하지 않았다. 두 실행은 각각 2.75초, 2.67초의 단일 측정이므로 속도 차이를 주장할 수 없다. 후보 수가 달라진 결과는 검색 제한 확인일 뿐 관련도 평가가 아니다.

## 자원과 비용

가장 큰 파일럿 실행은 총 434.28초가 걸렸고, 실제 모델 추론은 3,155개 상태에 258.84초였다. 동일 질의의 완전 캐시 재실행은 0.0666초에 새 추론 상태 없이 같은 순위를 냈다. 이는 차가운 첫 실행과 정확히 같은 입력의 캐시 비교다. 프로세스 RSS 최고값은 약 2.74GB, MPS 종료 시 할당량은 약 1.30GB였다. 두 값은 합산하거나 GPU 최고 사용량으로 볼 수 없다. 시험기는 36GB였으므로 Laya 문서에 제시된 4GB 메모리 조건은 검증하지 못했다. [모델 문서](https://unsloth.ai/docs/models/decision-laya)

Laya 로컬 추론은 실제 실행했지만, 답변 생성·채점에 유료 클라우드 LLM을 부른 횟수는 0회였다. API 기준 GPT-6 Luna Standard 단문맥은 100만 입력 토큰당 $0.10, 캐시 입력 $0.01, 출력 $0.50다. 공개 평가에서 Laya 토크나이저로 센 원문 상위10 중앙값 32,258개가 OpenAI 청구 토큰 수와 같다고 가정하면 입력 비용은 약 $0.0032다. 그러나 Laya/mmBERT 토큰은 OpenAI 청구 토큰이 아니므로 실제 비용이나 절감액이 아니다. 산식은 `저장된 OpenAI 입력 토큰 × 단가 / 1,000,000 − 로컬 시간 × 시간당 비용 − 상각된 구축·동기화 비용`이며, 변수와 청구 토큰이 없어 순절감은 계산할 수 없다. Codex 구독/크레딧은 API 가격과 별도로 집계되고 실제 청구액은 확인되지 않았다. [Luna API 가격](https://developers.openai.com/api/docs/models/gpt-6-luna) · [API 가격표](https://developers.openai.com/api/docs/pricing) · [Codex 요금 안내](https://learn.chatgpt.com/docs/pricing)

실험을 준비하고 수집·디버깅하는 데 상당한 Codex 오케스트레이션이 필요했다. 2026-09-30 09:20 KST 목표 스냅샷은 누적 harness 1,186,947 토큰과 5,966초를 기록했다. 이는 청구 입력·출력·캐시 토큰이나 달러가 아니다. 초기 전문 워커는 고정된 GPT-6 Astra 역할을 사용했고, 본 보고서의 초안·정리는 요청대로 GPT-6 Luna max를 사용했다. 부모 모델은 자동 변경되지 않았다. 이 기록만으로 설정비 최소화나 순절감을 주장할 수 없으며, Mac 전력과 사람 시간 비용도 측정하지 않았다. 현재 확인된 것은 로컬 추론 API 호출료가 0이라는 점뿐이다.

## 추가 실험: 실제 링크를 따라가는 결정형 탐색

사용자가 공유한 글은 Jev가 ‘고무오리’에서 ‘컴퓨터 알고리즘’으로 이동하는 사례를 설명한다. TypeSafe의 공식 소개에도 현재 문서의 링크만 따라 목표 문서에 도달하는 Wikiracing 시연이 있으며, ‘Rubber Duck’ 시작 사례를 언급한다. 다만 이번에는 영상을 재생하거나 해당 목표까지의 경로·성공률·비용을 재현하지 않았다. 소개 글은 비교 LLM의 추론 설정이 낮았다는 점과, 선택지가 255개를 넘으면 먼저 점수를 매긴 뒤 선택하는 두 단계 구성을 사용한다는 조건도 밝힌다. 이 시연의 비교 수치를 사내 위키나 로컬 Laya의 성능으로 옮겨 해석할 수는 없다. [TypeSafe 공식 소개](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

이 방식은 문서마다 관련도를 매겨 정렬하는 실험과 다르다. Jev의 `Choice`와 Laya는 상태와 정해진 선택지를 받아 후보 하나를 반환하는 인터페이스를 제공한다. 이번에는 질문·현재 문서의 정규화된 앞부분 최대 220토큰·방문 경로·링크를 발견한 부모 경로를 상태로 넣고, 다음 문서의 경로와 링크 문맥을 A~E 선택지로 넣었다. 정답 ID와 정답 경로는 질문 탐색의 모델 입력에 넣지 않았다. 이름을 아는 목표 탐색은 목표 이름 자체가 질의에 포함되는 별도 과제다. [Jev Choice](https://docs.typesafe.ai/primitives/choice) · [Laya 모델 카드](https://huggingface.co/convaiinnovations/laya-multilingual)

공개 27문서와 그 사이의 실제 방향 링크 41개를 고정했다. 코드 블록 속 링크, 외부·범위 밖 링크, 자기 링크는 탐색 대상에서 제외했고 인위적인 연결은 추가하지 않았다. Confluence는 다시 GET한 27개 사본을 사용했다. 읽기 준비 단계의 HTTP는 총 28회 모두 200이었다. 원문 링크와 Confluence 페이지 ID의 대응표로 동일 문서 ID를 찾았으며, 로컬·사본의 링크 순서도 같았다. 이는 원문 링크가 모두 Confluence 내부 링크로 다시 작성됐다는 뜻은 아니다.

추론 전에 고정한 사례는 24개다. 구조상 최단 경로가 2~3인 정렬된 첫 여섯 쌍을 이름 목표로 골랐다. 이 여섯 쌍은 모두 같은 저장소 README에서 출발하므로 다양한 시작점의 성능으로 볼 수 없다. 기존 테스트 질문 7개와 답 없는 질문 1개는 두 저장소 README에서 각각 시작했다. 정답에 맞춰 시작점을 골라 주지 않았으며, 질문 탐색 14건 중 경로가 있는 것은 7건이다. 별도로 연결되지 않은 두 저장소 사이 탐색 2건을 넣었다. [고정 사례](results/graph-cases.json)

시작 문서를 포함해 고유 문서 읽기를 최대 8개, 한 번의 후보 메뉴를 최대 5개로 제한했다. FIFO·BM25·Laya는 방문한 문서에서 발견한 미선택 링크를 모두 보관하고 같은 순서의 첫 5개 창에서 다음 읽기를 골랐다. 창 밖 후보는 나중에 남아 있으며 방문한 문서는 다시 읽지 않는다. `strictLaya`는 현재 문서의 링크만 고르고 이전 후보로 돌아오지 않는다. 따라서 앞의 세 방식은 링크가 연결된 탐색 후보 큐의 읽기 순서 비교이며, 현재 페이지의 링크만 타는 Wikiracing과 구분해야 한다. 선택지가 하나이면 Laya 추론을 생략했다. 전역 초기 검색과 탐색 중 추가 검색은 실행하지 않았다.

| 방식 | 이름 목표 6건: 도달 / 총 읽기 | 경로 있는 질문 7건: 도달 / 총 읽기 | 전체 24건: 도달 / 총 읽기 |
| --- | --- | --- | --- |
| FIFO | 1/6 · 48개 | 4/7 · 42개 | 5/24 · 164개 |
| BM25 링크 메타데이터 | 3/6 · 40개 | 4/7 · 40개 | 7/24 · 154개 |
| Laya 후보 큐 | 3/6 · 로컬 43개 / 사본 42개 | 5/7 · 로컬 37개 / 사본 38개 | 8/24 · 154개 |
| strictLaya 현재 링크만 | 1/6 · 15개 | 1/7 · 16개 | 2/24 · 57개 |

도달 수는 양쪽 사본에서 전부 같았다. 질문 14건 전체 기준 Laya는 5/14, BM25는 4/14다. 경로가 없는 7건을 제외한 5/7을 시스템 전체 검색 성공률로 읽으면 안 된다. Laya는 IME 질문에서 BM25가 예산 안에 찾지 못한 문서를 7회 읽기로 찾았고, origin 격리 질문은 로컬 3회로 BM25 8회보다 빨랐다. 반대로 토큰 프로필 위치 질문은 Laya 6회, BM25 2회였다. 이름 목표에서는 같은 3건을 찾는 데 더 읽었고 전체 읽기도 줄지 않았다. `strictLaya`의 적은 읽기는 막다른 길에서 일찍 멈춘 결과라 절감 성공으로 평가하지 않는다.

평가기는 알려진 정답 ID를 읽으면 종료하는 **평가용 오라클**이다. 모델이 충분한 근거를 스스로 판단해 종료하는 기능은 구현하거나 평가하지 않았다. 답 없는 질문과 경로 없는 대조군은 성공으로 처리하지 않았으며, Laya 후보 큐도 6~8개를 읽고 큐 소진이나 예산으로 끝났다. 이는 “답이 없다”는 판단 정확도의 검증이 아니다. 표본은 작고 기존 질문을 재사용했으며, 선택 정책의 하이퍼파라미터를 결과에 맞춰 다시 조율하지 않았다.

| 실제 실행 비용 | 로컬 Markdown | Confluence 읽기 사본 |
| --- | ---: | ---: |
| 캐시 없는 새 Laya 상태 | 127개 | 126개 |
| 새 상태의 모델 입력 토큰 | 69,558 | 69,233 |
| 모델 준비 / 추론 / 전체 | 4.45 / 8.51 / 14.37초 | 3.08 / 8.23 / 12.91초 |
| 프로세스 peak RSS | 2,718,482,432바이트 | 2,717,483,008바이트 |
| 동일 24사례 × 4정책 재실행 | 0.650초 · 새 추론 0개 | 0.727초 · 새 추론 0개 |

두 캠페인은 별도 프로세스·별도 캐시로 순차 실행했다. 한 캠페인 안에서는 후보 큐와 strict 정책이 같은 상태 캐시를 공유하므로 strict의 새 호출 수를 독립적인 첫 실행 비용으로 비교하지 않는다. 동일 상태 반복에서는 경로가 모두 같았지만 사본 간 경로는 96개 중 83개만 같았다. 텍스트의 왕복 변환이 다른 선택을 만들 수 있으며, 같은 도달 수가 경로 불변성을 뜻하지 않는다. BM25는 모델 호출 0회였고 인덱스 처리 총시간은 각각 약 0.006초였다. 이 숫자는 한 번의 실행이며 문서 동기화, HTTP 지연과 답변 생성 비용은 제외됐다.

실제 SDK 입력은 최대 로컬 664토큰, 사본 661토큰, 질문 헤드는 최대 165토큰이었다(`max_len=1024`, `head_max_len=255`). SDK가 추가로 버린 상태 토큰은 0개였다. 그 전에 긴 현재 문서를 짧은 앞부분으로 줄이며 최대 약 20,373토큰을 제외했다. 원문 길이 계수를 위한 토큰화에서 8,192를 넘는 길이 경고가 나왔지만 이 원문 전체를 모델에 전달한 것은 아니다. 앞부분 압축이 후반부의 중요한 단서를 놓칠 가능성은 남아 있다.

추론 프로세스는 macOS 네트워크 차단 샌드박스와 `HF_HUB_OFFLINE=1`로 실행했다. 새 수집·모델 설치·유료 답변/채점 API 호출은 없었다. Codex 조율은 Luna max 배정을 시도했으나 현재 등록 역할을 강제하는 실행 훅이 막았다. 제한된 구현 작업자 하나만 기존 고정 모델로 사용했고 부모 모델도 바뀌지 않았다. 이번에는 Luna로 비용을 내렸다고 주장할 수 없다. Confluence의 개인 문서 20건 보호 실패와 전체 계정 수집 미완료는 이전 상태 그대로다. [측정 집계와 사례별 결과](results/graph-summary.json)

질문 탐색에서는 초기 후보를 저렴한 로컬 검색으로 얻고, Laya가 다음 읽기를 고르도록 하는 조합이 적합한 가설이다. 다만 선택 확률이 높다고 답의 근거가 충분한 것은 아니다. 필요한 주장마다 현재 문서의 실제 근거를 확인한 뒤 LLM에 전달하고, 부족하면 남겨 둔 후보나 새 검색으로 돌아가야 한다. 링크가 풍부하면 읽는 양을 줄일 가능성이 있지만, 연결이 끊겼거나 제목이 모호하면 검색 비용이 오히려 늘 수 있다. Jev 시연만으로 Laya의 판단 품질·보정·비용 절감이 같다고 가정하지 않는다.

## 권고

우선 로컬 BM25 인덱스, 문서 메타데이터, 정규화된 텍스트 구간과 정확한 입력 키 기반 캐시를 사용한다. 링크 기반 Laya는 남은 후보를 보관하는 방식에서 국소적인 개선을 보였지만, 전체 읽기를 줄이지 못했고 모델 호출이 없는 BM25보다 추론이 추가됐다. 기본 선택기는 BM25로 두고, Laya는 모호한 후보의 선택을 돕는 선택 사항으로 검토하는 편이 비용에 맞다. 그 혼합 정책의 이점은 이번에 측정하지 않았다. 컬렉션 라우팅과 0.7 점수 기준은 검색이나 답변을 차단하는 규칙으로 사용하지 않는다.

실사용 검토를 다시 시작하려면 독립된 더 큰 질문 세트에서 후보 재현율과 순위 품질을 별도로 측정하고, 답이 없는 사례로 점수 보정을 검증해야 한다. 메모리 제한이 중요한 환경은 해당 기기에서 peak RSS와 MPS 최고 메모리를 직접 재측정해야 한다. 이미 승인된 본인 자료 복사는 유효한 제한을 먼저 확인한 뒤 진행한다. 제한을 적용할 수 없는 상태에서 다른 사람도 읽을 수 있는 범위에 게시하려면 그 공개 범위에 대한 별도 승인이 필요하다.
