# Laya 로컬 위키 검색 타당성 보고서

**갱신일:** 2026-10-01 KST · **판정:** 로컬 실행과 Confluence 연동은 가능하다. 확장 검색에서는 Laya가 BM25보다 나빴으며, 후보 선택의 순비용 절감은 입증되지 않았다.

Laya는 Apple M3 Pro에서 CPU와 MPS로 실행됐다. 최초 27문서 링크 실험의 일부 개선을 9,434문서로 확장해 확인하니, 양성 질문 10개에서 전역 BM25의 Hit@3은 7개, Laya는 후보 10개에서 2개, 40개에서 1개였다. 공개 2,238문서의 경로 정보를 넣은 별도 선택 실험에서도 Laya와 BM25 모두 6개 중 3개를 찾았다. 따라서 지금은 BM25를 기본 검색기로 쓰는 편이 정확도와 실행 비용에 맞는다. [실험 방법과 재현 명령](README.md)

## 텍스트 전체 범위로 확장한 추가 검증

이 절은 최초 파일럿과 별도의 캠페인이다. 원시 자료·선택 경로·개인 문서명과 URL은 계속 무시되는 로컬 디렉터리에 보관했다. GitHub에는 [집계](results/text-expansion-summary.json), [공개 질문](results/text-expansion-cases.public.json), [경로 선택 질문](results/metadata-cases.json)만 추가한다. 공개 질문 파일에서는 비공개 저장소의 동일 내용 별칭 ID도 제외했다. 원래 평가의 별칭 라벨을 그대로 재현하려면 로컬 고정 코퍼스와 원시 사례 파일이 필요하다.

소유 GitHub 저장소 66개를 조회했다. 65개는 읽을 수 있는 기본 브랜치 트리가 있었고 하나는 기본 브랜치가 없었다. Markdown/MDX/RST/TXT 문서 9,434개, UTF-8 71,382,282바이트를 검증해 수집했다. 공개 2,238개와 비공개 7,196개이며, 기존 512 KiB 제한을 넘는 의미 있는 텍스트 6개도 보존했다. 후보 중 129개는 비밀 값으로 보이는 내용 44개, 빈 파일 82개, 잘못된 UTF-8 2개, 바이너리 1개로 각각 기록했다. 의존성·빌드 산출물 경로 제외 5개도 명시했다. 가져온 Git blob 4,821개를 검사해 미디어·비문서 blob이 없음을 확인했다. 누락 이유를 설명하는 인벤토리라는 뜻이지 모든 원문을 무조건 수집했다는 뜻은 아니다.

공개 텍스트 2,238개를 실험 공간에 모두 게시하고 다시 GET해 문서 ID·제목·부모·버전과 준비한 텍스트의 해시를 대조했다. 중복 제거와 큰 텍스트 분할 후 콘텐츠 2,322페이지, 목록·메타데이터 포함 2,436페이지다. 고유 준비 텍스트는 25,644,546바이트이며 실제 HTTP 전송량은 별도로 계측하지 않았다. 첨부물 업로드는 0회다. [확장 위키 목록](https://koreaplayer99-confluence-dev.atlassian.net/wiki/pages/viewpage.action?pageId=3834037) 목록은 저장소·문서 경로와 원문 링크를 제공하며, 본문은 텍스트 코드 영역에 보관했다. Notion의 원래 페이지 트리를 재현하는 구조는 아니다.

실제 Cloud 시험에서는 접기 매크로 안에 직접 넣은 코드 매크로의 메타데이터가 사라졌다. 읽기 검증이 이를 잡아 중단했다. `ac:rich-text-body`로 감싼 후 3문서 시험과 전체 게시가 통과했다. 실패한 시험 페이지 12개는 새로 읽은 본인 작성·제목·부모·버전을 확인하고 정리했다. 기존 파일럿 공개 문서 27개도 새로 읽어 그대로 확인했다. 게시 중 오류 응답에 대한 자동 POST 재시도는 없었다.

부모 세션에서 관련 Node 테스트 67개와 Python 테스트 38개가 통과했다. CLI 입력 오류·중단 후 재개·바이너리와 미디어 제외·대용량 Unicode·서명 URL·권한 실패·읽기 불일치·실제 SDK 입력 경계를 확인했다. 단위 테스트와 별도로 실제 Cloud 게시·읽기, 브라우저 목록 링크와 본문 표시, 네트워크를 차단한 MPS 추론을 관찰했다.

Notion은 개인 TwoTwo 워크스페이스만 대상으로 한다. 기본 보기, Markdown/CSV, 파일·이미지 제외로 전체 내보내기를 요청했지만 다운로드 파일은 아직 확보하지 못했다. 별도 로그인 독자에서도 검색 1,000건과 기본 DB 조회 100건은 상한에 걸렸고, 메타데이터만 가져온 페이지의 자식 목록은 빈 것으로 보였다. 선언된 자식 ID를 실제로 읽은 뒤 변환해야 본문이 나왔다. 현재는 자식·컬렉션 행을 순회하는 텍스트 수집을 진행 중이다. TIL의 필터 없는 표 보기는 커서 4페이지, 355개 고유 행, `has_more=false`까지 확인했다. 이는 해당 보기의 검증이며 워크스페이스 전체 완전성을 뜻하지 않는다. 전체 커버리지와 개인 자료의 Confluence 게시 결과는 아직 미완료다.

추론 전 2026-09-30 12:41:20 UTC에 질문 14개를 고정했다. 보정 2개, 테스트 양성 10개, 답 없는 대조군 2개다. 정답은 확인한 공개 문서와 바이트가 같은 별칭이며, 다른 관련 문서까지 빠짐없이 라벨링하지는 않았다. 코퍼스 해시는 `83b3f467fc10fff5e67dcfae24ab8827a7593539b5bf02b8af3e8c36b93dea36`이다. SDK와 모델 revision은 최초 실험과 같고, 네트워크 차단 macOS 샌드박스에서 MPS로 실행했다.

| 9,434문서·양성 테스트 10개 | 전역 BM25 Hit@3 | Laya Hit@3 | 초기 후보에 정답 포함 |
| --- | ---: | ---: | ---: |
| 후보 10개 | 7/10 | 2/10 | 7/10 |
| 후보 40개 | 7/10 | 1/10 | 7/10 |

전역 BM25는 코퍼스 전체에서 처음 정렬한 순서다. 기존 평가기가 후보 집합 안에서 새로 만드는 BM25와 혼동하면 안 된다. 후보 40개로도 세 질문의 알려진 정답을 얻지 못했고, Laya는 이미 확보한 정답의 순위도 떨어뜨렸다. 양성 질문의 Laya MRR은 각각 0.2772, 0.1059였다. 원시 결과의 테스트 집계는 대조군 2개도 포함해 분모가 12지만, 이 보고서의 정확도 표는 양성 10개만 사용한다.

열 질문의 원문 상위 10개 토큰 합은 633,964개, Laya가 선택한 세 구간 합은 후보 10개에서 8,727개, 40개에서 11,429개였다. 입력을 작게 만드는 것은 가능했지만 정답을 놓쳤으므로 성공한 비용 절감으로 평가하지 않는다. 모든 토큰 수는 Laya 토크나이저 기준이며 OpenAI 청구 토큰이 아니다. 논리적 SDK 입력 토큰을 여러 정책·반복 행에서 합산해 새 추론 비용으로 계산하지 않았다. 실제 새 상태는 1,111개, 고유 캐시 키는 1,103개였다. 같은 배치 안 중복 상태 8개가 추가 실행된 결과다. 반복에서는 새 상태 0개와 동일 순위가 확인됐다.

준비 5.39초, 인덱스 5.60초, 새 추론 69.41초, 전처리 등을 포함한 전체 170.21초였다. 프로세스 peak RSS는 2,422,898,688바이트다. 답 없는 두 대조군의 후보 40개 최고 점수는 약 0.761과 0.764였다. 이 점수는 보정된 정답 확률이나 충분한 근거의 판정이 아니다.

경로 정보가 도움이 되는지도 한 번만 좁혀 확인했다. 2026-09-30 14:26:37 UTC에 새로운 질문 6개와 답 없는 대조군 2개를 고정하고, 공개 2,238문서에서 제목·경로·본문 BM25 상위 40개를 메뉴로 만들었다. 질문은 세 원문에 집중돼 독립된 여섯 주제 표본은 아니다. 실제 위키의 방향 링크를 타는 과제와 구분되는 **가상 검색 후보 메뉴**다. 시작 메뉴를 포함해 최대 8회 읽기, 한 결정에 4개 선택지, 미선택 후보 보관을 고정했다. 정답 ID는 모델 상태에 넣지 않았고 결과를 보고 질문·프롬프트·예산을 바꾸지 않았다.

| 추가 선택 과제·양성 6개 | 로컬: 도달 / 읽기 | Confluence 텍스트: 도달 / 읽기 |
| --- | ---: | ---: |
| FIFO | 3/6 · 30회 | 3/6 · 30회 |
| BM25 | 3/6 · 30회 | 3/6 · 30회 |
| Laya 후보 큐 | 3/6 · 30회 | 3/6 · 30회 |
| 현재 후보만 보는 strictLaya | 3/6 · 12회 | 3/6 · 12회 |

30회에는 시작 메뉴 6회가 포함돼 실제 콘텐츠 읽기는 24회다. 후보 40개에 정답이 포함된 질문은 5/6이며 나머지 한 질문은 선택기로 복구할 수 없다. strict의 적은 읽기는 잘못 고른 문서에서 후보가 끊겨 종료한 결과다. Confluence 텍스트는 검증한 사본에서 준비했고, 메뉴 순서를 그대로 유지했다. 평가 중 HTTP 읽기는 0회다. 이 결과를 실시간 Confluence 검색의 지연·비용으로 해석할 수는 없다.

로컬은 새 상태 38개, 새 입력 19,559토큰, 추론 2.91초, 준비 포함 전체 7.64초였다. 사본은 로컬의 정확한 상태 캐시를 복사해 일치하는 키만 재사용했고 새 상태 27개, 새 입력 15,516토큰, 추론 2.16초, 전체 8.24초였다. 별도 무캐시 캠페인의 속도 비교가 아니다. 양쪽 peak RSS는 약 2.80GB·2.67GB, 정확히 같은 상태 재실행은 새 추론 0개였다. 32개 정책·사례 경로 중 29개가 같았고 도달 수는 모두 같았다. 종료는 알려진 문서 ID를 읽는 평가용 오라클이며, 근거가 부족하면 차순위를 자동으로 더 가져오는 충분성 판단은 검증하지 않았다.

## 접근 권한과 이번 추가 비용의 범위

기존 Google/Atlassian 로그인으로 인증할 수 있었다. 실제 토큰 화면에서 이전 토큰의 2026-09-30 만료를 확인하고, 같은 15개 범위로 새 토큰을 발급했다. 유효한 사용자·페이지 GET 200을 확인한 뒤 로컬 프로필을 교체했다. 새 만료일은 2026-10-07이다. 토큰과 인증 코드는 출력하거나 저장소에 넣지 않았다.

관리 화면은 Confluence Free, 활성 인간 사용자 1명인 본인, 대기 초대 0명을 보여 줬다. 공간 권한 API의 모든 항목에서 익명·비라이선스 접근은 꺼져 있었고 읽기 주체로 앱 두 개도 확인됐다. Free는 페이지 권한 제한을 적용할 수 없고 익명·공개 링크를 지원하지 않는다. 따라서 현재 확인된 사이트에서 외부인이 링크만으로 읽는 상태는 아니다. 앞으로 사람을 초대하면 공간 권한으로 게시한 개인 자료를 읽을 수 있으므로 본인만의 페이지 제한과 같은 보장이 아니다. [Free 권한](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-in-the-free-edition-of-confluence-cloud/) · [공개 링크](https://support.atlassian.com/confluence-cloud/docs/how-secure-are-public-links/)

갱신한 API로도 내용 없는 `private=true` 생성 시험은 404였다. 이 실패 후 개인 원문을 일반 페이지로 바꿔 올리지 않았다. 현재 확인한 공간 권한으로 비공개 GitHub·개인 Notion 텍스트를 복사하는 별도 승인은 대기 중이다. 계정 전체 수집·개인 자료 이관을 완료했다고 보고하지 않는다.

이번 확장에서는 유료 답변·채점 LLM API를 호출하지 않았다. Luna max 사용은 현재 역할을 고정하는 실행 제약과 Aside 계정의 가용 모델 때문에 성사되지 않았다. 동시에 활성화한 구현 작업자는 한 명으로 제한하고, 대량 수집·게시·집계는 직접 스크립트로 처리했다. 이를 Luna로 실행했다고 주장하지 않는다. 목표 드라이버의 중단 시점 스냅샷은 누적 harness 902,663토큰·5,844초였고, 중단 이후의 계속 작업은 포함하지 않는다. 이는 청구 토큰이나 달러가 아니며, 실제 Codex 요금·전력·사람 시간·초기 동기화 비용은 측정하지 않았다. 준비 과정이 저렴했다거나 전체 순비용이 줄었다는 결론도 낼 수 없다.

현재 근거에 맞는 구성은 로컬 동기화와 BM25로 후보를 찾고, 작은 실제 근거 구간을 최종 LLM에 전달하는 방식이다. Laya의 예측값을 근거 충분성으로 사용하지 않는다. 다음 후보를 더 읽는 흐름은 남겨 둘 수 있지만 그 조건은 별도 검증이 필요하다. 이번 추가 캠페인에서는 Laya를 기본 검색·재정렬기로 채택할 근거가 없었다.

## 무엇을 실제로 시험했나

M3 Pro 11코어, 메모리 36GB, macOS 26.6.2, Python 3.12.13에서 실행했다. 순위 평가는 MPS, `max_len=1024`, 본 평가 `head_max_len=192`로 돌렸다. 평가기는 BM25 후보에서 문서당 최대 두 구간을 골라 Laya 점수를 매기고, 상위 세 문서를 최종 컨텍스트로 남겼다. 계정 전체 내보내기는 끝나지 않았다. GitHub 소유 저장소 66개의 인벤토리 중 선택한 공개 저장소 2곳에서 Markdown 문서 27개를 모두 수집했다. 별도로 수집 가능한 로컬 문서는 3,627개였지만 이를 전체 계정 자료로 간주하지 않았다. Notion 캡처 606개도 부분 자료다. 파일당 512 KiB 제한을 적용했고 Markdown 본문만 평가했다. 첨부물은 링크로 남겼으며 내려받거나 OCR하지 않았다.

고정 파일에는 민감한 원문을 넣지 않았다. [summary.json](results/summary.json)은 집계 결과이고 [public-cases.json](results/public-cases.json)은 공개 자료를 대상으로 사전 지정한 질문과 해시 ID만 담는다. 원문 캡처, 개인 문서명·질문·URL, HTTP 본문과 캐시는 로컬 `artifacts/laya-wiki/`에 남겨야 한다.

## 검색 결과

Hit@3은 관련 문서가 상위 세 결과 안에 든 질의 수다. 아래 분모는 각 테스트 코호트의 양성 질의 수이며, 관련성은 사전에 지정한 “알고 있는 정답 문서” 기준이다.

| 평가 | BM25 기준 | Laya 설정 | 관찰 |
| --- | ---: | ---: | --- |
| 47문서 파일럿, 양성 11건 | 6/11 | prefix 상위10: 5/11; 청크 상위10: 7/11; 정규화 상위10: 8/11 | 정규화 47문서 전체에서는 5/11 |
| 공개 GitHub·Confluence 사본 대조, 양성 7건 | 로컬 BM25: 3/7 | 로컬 정규화 상위10: 3/7, 전체27: 3/7; Confluence 상위10: 3/7, 전체27: 2/7 | 상위10 후보에 정답이 포함된 비율은 5/7 |
| 로컬 3,627문서 사용 가능 집합, 양성 4건 | 상위10 기준 2/4 | 정규화 상위10: 2/4, 상위50: 1/4 | 양성 질의 중앙 시간 1.44초와 6.69초 |

후보 누락과 재순위화 오류는 다르게 봐야 한다. 공개 평가에서 상위10 후보가 정답을 포함한 질의는 5/7이므로 나머지 2건은 재순위화만으로 복구할 수 없다. 후보를 모두 넣은 로컬 공개 집합에서는 정규화 순위가 BM25와 같은 3/7이었고, 47문서 파일럿 전체에서는 BM25 6/11보다 낮은 5/11이었다. 파일럿 정규화 순위의 MRR도 상위10에서 0.5833, 전체47에서 0.2892였고 후보 포함률은 각각 9/11, 11/11이었다. 반대로 파일럿 상위10 정규화 결과 8/11은 탐색 신호지만, 같은 작은 코호트에서 나온 값이라 일반화 성능으로 볼 수 없다.

평가 질의는 파일럿 14건(보정 2, 테스트 양성 11, 답이 없는 질의 1)이었다. 라벨은 정답 문서 한 개만 확인했으며 모든 관련 문서를 빠짐없이 표시하지 않았다. 표본도 작고 무작위 표본이 아니므로 백분율을 안정적인 제품 정확도로 해석할 수 없다. 응답 생성, 사용자 효용, 다중 문서 근거 품질은 측정하지 않았다.

고정 임계값 0.7도 신뢰할 수 없었다. 답이 없는 테스트에서 정규화 47문서 결과의 최고 관련도 점수는 0.9977, 세 번째 점수는 0.7068이었다. 따라서 높은 점수나 임계값 조기 종료를 “답을 찾았다”는 확신도로 취급하면 안 된다. 답이 없는 사례가 하나라 이 값은 보정 결과가 아니라 실패 가능성을 보여주는 예다. 인공 tail 입력 한 건에서는 prefix가 9,580 토큰을 잘라냈고 관련도 점수는 prefix 0.2918, 청크 0.6055였다. 같은 한 건에서 기준 문항 순서를 뒤집자 관련도 점수도 0.2918에서 0.1764로 바뀌었다. 이는 견고성 입증이 아니라 단일 프로브의 경고 신호다.

반복 캐시는 동일 질의에서 추가 추론 상태 0개와 같은 순위를 돌려줬다. 이는 정확히 같은 입력의 캐시 재사용 결과일 뿐, 새 질의의 일반 지연시간을 뜻하지 않는다. 캐시 키는 문서 내용·제목, 질의, 구간, 모델 revision, SDK, 장치, 스키마, 길이, 배치 크기와 정책을 반영했다.

## 컬렉션 라우팅과 Confluence 연동

수동으로 만든 5분류 라우터는 문서 본문 토큰 0개, 입력 1,904토큰으로 질문 14개를 평가했다. 실제 라우팅 추론은 네트워크를 차단한 상태에서 실행됐고 모델 처리 시간은 0.775초였다. 보정 세트는 2/2였지만 테스트 분류 정확도는 4/12(33%)였다. 테스트 양성 11건에서 라우팅 후 Hit@3은 1/11, 모든 문서에서 BM25를 실행한 기준은 4/11이었다. 라우터 출력은 현재 후보 검색을 차단하는 필터로 쓰지 말아야 한다. 향후 다시 시험하더라도 참고용 힌트로 제한하는 편이 맞다.

공개 GitHub 자료 27개를 Confluence 사본에 실제로 쓰고 다시 읽어 무결성을 확인했다. [검증한 실험 루트](https://koreaplayer99-confluence-dev.atlassian.net/wiki/pages/viewpage.action?pageId=3506179) 따라서 공개 원본 범위의 왕복 연동은 확인했지만, 개인 자료를 포함한 47문서 이관은 확인하지 못했다. 개인 문서 생성용 `private=true` POST는 HTTP 404를 반환했고 페이지 ID를 받기 전이어서 그 요청 뒤에는 ACL 쓰기가 없었다.

별도로 원문 없이 빈 임시 페이지를 만들어 현재 사용자와 페이지 작성자 읽기를 확인한 뒤, 실제 페이지 제한 PUT을 시도했다. 페이지 생성·사용자 확인·작성자 읽기는 각각 200이었지만 제한 PUT은 403이었다. 새로 GET하고 삭제 전 조건을 확인한 뒤 DELETE 204로 정리했으며, 후속 GET에서 페이지 상태가 `trashed`임을 확인했다. 이 안전한 프로브는 현재 프로필/사이트에서 요청한 제한을 적용하지 못함을 보여준다. 403의 원인이 플랜, 토큰 범위, 계정 권한 또는 공간 권한 중 무엇인지는 확인되지 않았으며 Free 플랜의 증거로 볼 수 없다.

현재 사이트의 과금 플랜은 확인되지 않았고, 검증 루트에 직접 제한이 설정되지 않았으며 상속·익명 접근도 감사하지 않았다. Atlassian 문서에 따르면 Free는 페이지·공간 권한을 사용자 지정할 수 없고 Standard/Premium은 페이지 제한을 지원하지만, 이 실험의 404와 403만으로 현재 플랜을 판정할 수는 없다. [Atlassian 권한 문서](https://support.atlassian.com/confluence-cloud/docs/manage-permissions-in-the-free-edition-of-confluence-cloud/) 개인 Notion 문서는 Confluence에 한 건도 올리지 않았다.

실시간 검색에서 첫 요청은 제한 10개와 같은 10개 후보를 반환해 잘렸을 가능성이 표시됐다. 제한 20개 요청은 후보 17개, HTTP 18회, 응답 253,152바이트를 기록했고 제한에 도달하지 않았다. 두 실행은 각각 2.75초, 2.67초의 단일 측정이므로 속도 차이를 주장할 수 없다. 후보 수가 달라진 결과는 검색 제한 확인일 뿐 관련도 평가가 아니다.

## 자원과 비용

가장 큰 파일럿 실행은 총 434.28초가 걸렸고, 실제 모델 추론은 3,155개 상태에 258.84초였다. 동일 질의의 완전 캐시 재실행은 0.0666초에 새 추론 상태 없이 같은 순위를 냈다. 이는 차가운 첫 실행과 정확히 같은 입력의 캐시 비교다. 프로세스 RSS 최고값은 약 2.74GB, MPS 종료 시 할당량은 약 1.30GB였다. 두 값은 합산하거나 GPU 최고 사용량으로 볼 수 없다. 시험기는 36GB였으므로 Laya 문서에 제시된 4GB 메모리 조건은 검증하지 못했다. [모델 문서](https://unsloth.ai/docs/models/decision-laya)

Laya 로컬 추론은 실제 실행했지만, 답변 생성·채점에 유료 클라우드 LLM을 부른 횟수는 0회였다. API 기준 GPT-6 Luna Standard 단문맥은 100만 입력 토큰당 $0.10, 캐시 입력 $0.01, 출력 $0.50다. 공개 평가에서 Laya 토크나이저로 센 원문 상위10 중앙값 32,258개가 OpenAI 청구 토큰 수와 같다고 가정하면 입력 비용은 약 $0.0032다. 그러나 Laya/mmBERT 토큰은 OpenAI 청구 토큰이 아니므로 실제 비용이나 절감액이 아니다. 산식은 `저장된 OpenAI 입력 토큰 × 단가 / 1,000,000 − 로컬 시간 × 시간당 비용 − 상각된 구축·동기화 비용`이며, 변수와 청구 토큰이 없어 순절감은 계산할 수 없다. Codex 구독/크레딧은 API 가격과 별도로 집계되고 실제 청구액은 확인되지 않았다. [Luna API 가격](https://developers.openai.com/api/docs/models/gpt-6-luna) · [API 가격표](https://developers.openai.com/api/docs/pricing) · [Codex 요금 안내](https://learn.chatgpt.com/docs/pricing)

실험을 준비하고 수집·디버깅하는 데 상당한 Codex 오케스트레이션이 필요했다. 2026-09-30 09:20 KST 목표 스냅샷은 누적 harness 1,186,947 토큰과 5,966초를 기록했다. 이는 청구 입력·출력·캐시 토큰이나 달러가 아니다. 초기 전문 워커는 고정된 GPT-6 Astra 역할을 사용했고, 본 보고서의 초안·정리는 요청대로 GPT-6 Luna max를 사용했다. 부모 모델은 자동 변경되지 않았다. 이 기록만으로 설정비 최소화나 순절감을 주장할 수 없으며, Mac 전력과 사람 시간 비용도 측정하지 않았다. 현재 확인된 것은 로컬 추론 API 호출료가 0이라는 점뿐이다.

## 추가 실험: 실제 링크를 따라가는 결정형 탐색

사용자가 공유한 글은 Jev가 ‘고무오리’에서 ‘컴퓨터 알고리즘’으로 이동하는 사례를 설명한다. TypeSafe의 공식 소개에도 현재 문서의 링크만 따라 목표 문서에 도달하는 Wikiracing 시연이 있으며, ‘Rubber Duck’ 시작 사례를 언급한다. 다만 이번에는 영상을 재생하거나 해당 목표까지의 경로·성공률·비용을 재현하지 않았다. 소개 글은 비교 LLM의 추론 설정이 낮았다는 점과, 선택지가 255개를 넘으면 먼저 점수를 매긴 뒤 선택하는 두 단계 구성을 사용한다는 조건도 밝힌다. 이 시연의 비교 수치를 사내 위키나 로컬 Laya의 성능으로 옮겨 해석할 수는 없다. [TypeSafe 공식 소개](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

이 방식은 문서마다 관련도를 매겨 정렬하는 실험과 다르다. Jev의 `Choice`와 Laya는 상태와 정해진 선택지를 받아 후보 하나를 반환하는 인터페이스를 제공한다. 이번에는 질문·현재 문서의 정규화된 앞부분 최대 220토큰·방문 경로·링크를 발견한 부모 경로를 상태로 넣고, 다음 문서의 경로와 링크 문맥을 A~E 선택지로 넣었다. 정답 ID와 정답 경로는 질문 탐색의 모델 입력에 넣지 않았다. 이름을 아는 목표 탐색은 목표 이름 자체가 질의에 포함되는 별도 과제다. [Jev Choice](https://docs.typesafe.ai/primitives/choice) · [Laya 모델 카드](https://huggingface.co/convaiinnovations/laya-multilingual)

공개 27문서와 그 사이의 실제 방향 링크 41개를 고정했다. 코드 블록 속 링크, 외부·범위 밖 링크, 자기 링크는 탐색 대상에서 제외했고 인위적인 연결은 추가하지 않았다. Confluence는 다시 GET한 27개 사본을 사용했다. 읽기 준비 단계의 HTTP는 총 28회 모두 200이었다. 원문 링크와 Confluence 페이지 ID의 대응표로 동일 문서 ID를 찾았으며, 로컬·사본의 링크 순서도 같았다. 이는 원문 링크가 모두 Confluence 내부 링크로 다시 작성됐다는 뜻은 아니다.

추론 전에 고정한 사례는 24개다. 구조상 최단 경로가 2~3인 정렬된 첫 여섯 쌍을 이름 목표로 골랐다. 이 여섯 쌍은 모두 같은 저장소 README에서 출발하므로 다양한 시작점의 성능으로 볼 수 없다. 기존 테스트 질문 7개와 답 없는 질문 1개는 두 저장소 README에서 각각 시작했다. 정답에 맞춰 시작점을 골라 주지 않았으며, 질문 탐색 14건 중 경로가 있는 것은 7건이다. 별도로 연결되지 않은 두 저장소 사이 탐색 2건을 넣었다. [고정 사례](results/graph-cases.json)

시작 문서를 포함해 고유 문서 읽기를 최대 8개, 한 번의 후보 메뉴를 최대 5개로 제한했다. FIFO·BM25·Laya는 방문한 문서에서 발견한 미선택 링크를 모두 보관하고 같은 순서의 첫 5개 창에서 다음 읽기를 골랐다. 창 밖 후보는 나중에 남아 있으며 방문한 문서는 다시 읽지 않는다. `strictLaya`는 현재 문서의 링크만 고르고 이전 후보로 돌아오지 않는다. 따라서 앞의 세 방식은 링크가 연결된 탐색 후보 큐의 읽기 순서 비교이며, 현재 페이지의 링크만 타는 Wikiracing과 구분해야 한다. 선택지가 하나이면 Laya 추론을 생략했다. 전역 초기 검색과 탐색 중 추가 검색은 실행하지 않았다.

| 방식 | 이름 목표 6건: 도달 / 총 읽기 | 경로 있는 질문 7건: 도달 / 총 읽기 | 전체 24건: 도달 / 총 읽기 |

도달 수는 양쪽 사본에서 전부 같았다. 질문 14건 전체 기준 Laya는 5/14, BM25는 4/14다. 경로가 없는 7건을 제외한 5/7을 시스템 전체 검색 성공률로 읽으면 안 된다. Laya는 IME 질문에서 BM25가 예산 안에 찾지 못한 문서를 7회 읽기로 찾았고, origin 격리 질문은 로컬 3회로 BM25 8회보다 빨랐다. 반대로 토큰 프로필 위치 질문은 Laya 6회, BM25 2회였다. 이름 목표에서는 같은 3건을 찾는 데 더 읽었고 전체 읽기도 줄지 않았다. `strictLaya`의 적은 읽기는 막다른 길에서 일찍 멈춘 결과라 절감 성공으로 평가하지 않는다.

평가기는 알려진 정답 ID를 읽으면 종료하는 **평가용 오라클**이다. 모델이 충분한 근거를 스스로 판단해 종료하는 기능은 구현하거나 평가하지 않았다. 답 없는 질문과 경로 없는 대조군은 성공으로 처리하지 않았으며, Laya 후보 큐도 6~8개를 읽고 큐 소진이나 예산으로 끝났다. 이는 “답이 없다”는 판단 정확도의 검증이 아니다. 표본은 작고 기존 질문을 재사용했으며, 선택 정책의 하이퍼파라미터를 결과에 맞춰 다시 조율하지 않았다.

두 캠페인은 별도 프로세스·별도 캐시로 순차 실행했다. 한 캠페인 안에서는 후보 큐와 strict 정책이 같은 상태 캐시를 공유하므로 strict의 새 호출 수를 독립적인 첫 실행 비용으로 비교하지 않는다. 동일 상태 반복에서는 경로가 모두 같았지만 사본 간 경로는 96개 중 83개만 같았다. 텍스트의 왕복 변환이 다른 선택을 만들 수 있으며, 같은 도달 수가 경로 불변성을 뜻하지 않는다. BM25는 모델 호출 0회였고 인덱스 처리 총시간은 각각 약 0.006초였다. 이 숫자는 한 번의 실행이며 문서 동기화, HTTP 지연과 답변 생성 비용은 제외됐다.

실제 SDK 입력은 최대 로컬 664토큰, 사본 661토큰, 질문 헤드는 최대 165토큰이었다(`max_len=1024`, `head_max_len=255`). SDK가 추가로 버린 상태 토큰은 0개였다. 그 전에 긴 현재 문서를 짧은 앞부분으로 줄이며 최대 약 20,373토큰을 제외했다. 원문 길이 계수를 위한 토큰화에서 8,192를 넘는 길이 경고가 나왔지만 이 원문 전체를 모델에 전달한 것은 아니다. 앞부분 압축이 후반부의 중요한 단서를 놓칠 가능성은 남아 있다.

추론 프로세스는 macOS 네트워크 차단 샌드박스와 `HF_HUB_OFFLINE=1`로 실행했다. 새 수집·모델 설치·유료 답변/채점 API 호출은 없었다. Codex 조율은 Luna max 배정을 시도했으나 현재 등록 역할을 강제하는 실행 훅이 막았다. 제한된 구현 작업자 하나만 기존 고정 모델로 사용했고 부모 모델도 바뀌지 않았다. 이번에는 Luna로 비용을 내렸다고 주장할 수 없다. Confluence의 개인 문서 20건 보호 실패와 전체 계정 수집 미완료는 이전 상태 그대로다. 질문 탐색에서는 초기 후보를 저렴한 로컬 검색으로 얻고, Laya가 다음 읽기를 고르도록 하는 조합이 적합한 가설이다. 다만 선택 확률이 높다고 답의 근거가 충분한 것은 아니다. 필요한 주장마다 현재 문서의 실제 근거를 확인한 뒤 LLM에 전달하고, 부족하면 남겨 둔 후보나 새 검색으로 돌아가야 한다. 링크가 풍부하면 읽는 양을 줄일 가능성이 있지만, 연결이 끊겼거나 제목이 모호하면 검색 비용이 오히려 늘 수 있다. Jev 시연만으로 Laya의 판단 품질·보정·비용 절감이 같다고 가정하지 않는다.

## 권고

우선 로컬 BM25 인덱스, 문서 메타데이터, 정규화된 텍스트 구간과 정확한 입력 키 기반 캐시를 사용한다. 링크 기반 Laya는 남은 후보를 보관하는 방식에서 국소적인 개선을 보였지만, 전체 읽기를 줄이지 못했고 모델 호출이 없는 BM25보다 추론이 추가됐다. 기본 선택기는 BM25로 두고, Laya는 모호한 후보의 선택을 돕는 선택 사항으로 검토하는 편이 비용에 맞다. 그 혼합 정책의 이점은 이번에 측정하지 않았다. 컬렉션 라우팅과 0.7 점수 기준은 검색이나 답변을 차단하는 규칙으로 사용하지 않는다.

실사용 검토를 다시 시작하려면 독립된 더 큰 질문 세트에서 후보 재현율과 순위 품질을 별도로 측정하고, 답이 없는 사례로 점수 보정을 검증해야 한다. 메모리 제한이 중요한 환경은 해당 기기에서 peak RSS와 MPS 최고 메모리를 직접 재측정해야 한다. 이미 승인된 본인 자료 복사는 유효한 제한을 먼저 확인한 뒤 진행한다. 제한을 적용할 수 없는 상태에서 다른 사람도 읽을 수 있는 범위에 게시하려면 그 공개 범위에 대한 별도 승인이 필요하다.
